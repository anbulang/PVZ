# PVZ 登录到房间到游戏闭环设计

## 目标

把当前“进入游戏页后再用顶部小条创建或加入房间”的体验，升级为稳定的三段闭环：

1. 玩家先进入登录页，填写轻量身份。
2. 进入独立房间设置页，创建或加入房间，确认双方阵营和准备状态。
3. 双方都准备后，自动进入游戏页开始在线对战。

本轮重点是把在线对战的入口、房间和游戏状态做清楚，让两台设备能按同一套流程稳定进入同一局，而不是继续把房间操作挤在游戏画布上方。

## 已确认选择

- 登录页采用轻量昵称登录，不做账号密码、注册、后端用户系统。
- 房间设置采用核心房间流，不做高级房主管理、观战、战绩或复杂对局参数。
- 页面流采用“登录页 → 房间设置页 → 游戏页”。
- 推荐实现采用单 app shell + 三个全屏 view。视觉上是独立页面，技术上保留现有 `index.html`、Canvas、WebSocket 客户端和游戏循环，降低回归风险。
- 房间页必须保证一方植物、一方僵尸，不能两台设备都成为植物方。
- 双方都准备后才进入游戏页；未准备阶段不能进入正式游戏操作。
- 登录页和房间设置页可以使用当前已有素材，并补充 Codex 生成的原创配套图片。

## 非目标

- 不做正式账号系统、密码登录、注册、找回密码。
- 不做公网匹配、房间列表、排行榜、战绩持久化。
- 不做房主踢人、转让房主、观战位、聊天系统。
- 不在本轮调整复杂对局参数，例如地图、时长、起始资源和压力档位。
- 不重写 Canvas 渲染、单位系统、在线房间核心状态机或 WebSocket 协议。

## 推荐架构

使用一个浏览器应用入口承载三个 view：

- `login`：登录页。
- `room`：房间设置页。
- `game`：游戏页。

URL 用查询参数表达当前页面和房间：

- `?view=login`
- `?view=room`
- `?view=room&room=ABCD`
- `?view=game&room=ABCD`

现有 `createOnlineClient()` 继续负责 WebSocket、房间快照、游戏快照和命令发送。新增轻量 UI 流程控制层只负责：

- 读取和保存玩家资料。
- 根据 URL 和房间状态切换 view。
- 把登录页和房间页按钮操作转成现有 `hostRoom()`、`joinRoom()`、`setReady()` 调用。
- 双方准备并收到 `playing` 状态后切到游戏页。

这样可以把页面体验做独立，同时避免拆散已经验证过的在线对战同步链路。

## 页面设计

### 登录页

登录页是玩家进入在线对战的第一屏。

内容：

- 游戏标题：`花园攻防在线双人版`。
- 昵称输入，默认可生成一个本地昵称。
- 头像偏好，使用植物风格和僵尸风格的小头像选项。
- 主按钮：`进入房间设置`。
- 如果 URL 带 `room`，登录后进入对应房间设置页。

数据：

- `playerName`：玩家昵称。
- `avatarId`：头像偏好。
- `lastUpdatedAt`：本地资料更新时间。

存储：

- 使用 `localStorage` 保存到 `pvz-player-profile`。
- 不发送密码或敏感信息。

视觉：

- 背景使用 Codex 生成的原创花园对战登录图。
- 叠加现有植物和僵尸视觉语言，但不使用营销式大段介绍。
- 移动端优先保证输入框、按钮和标题不挤压。

### 房间设置页

房间设置页是在线对战真正的 lobby。

创建房间状态：

- 显示玩家昵称和头像。
- 可输入房间名，默认 `向日葵战局`。
- 点击 `创建房间` 后调用 `hostRoom("plant")`。
- 房主默认占植物方。

加入房间状态：

- 可输入房间码。
- 如果 URL 已带 `room`，自动填入房间码。
- 点击 `加入房间` 后调用 `joinRoom(roomCode, "zombie")`。
- 如果植物方已占用，服务端分配僵尸方；如果僵尸方已占用，服务端分配剩余阵营；满员则显示错误。

房间已进入状态：

- 显示房间码。
- 显示邀请链接。
- 显示复制邀请链接按钮。
- 显示植物方和僵尸方两列席位。
- 每个席位展示昵称、头像、在线状态和准备状态。
- 本端只显示自己的准备按钮。
- 双方都在线后进入 `ready`，双方都准备后进入 `playing`。

视觉：

- 背景使用 Codex 生成的房间邀请卡或桌面图。
- 房间码和复制链接是高优先级信息。
- 阵营列固定左右布局：植物方在左，僵尸方在右。

### 游戏页

游戏页保留现有 Canvas 对战体验，但不再承担创建和加入入口。

进入条件：

- 在线房间状态为 `playing`。
- 本地已有玩家资料。
- 本端已分配到 `plant` 或 `zombie`。

页面内容：

- Canvas 游戏主体。
- 紧凑在线状态条，仅显示房间码、本端阵营、对手在线状态和当前阶段。
- 对局中不显示创建房间、加入房间、房间码输入或阵营选择。
- 掉线暂停、结束、再来一局继续沿用在线状态逻辑。

刷新行为：

- 游戏页刷新后，客户端用本地 `clientId` 和 URL 房间码恢复身份。
- 恢复成功后继续停留在游戏页。
- 恢复失败时退回房间设置页，并展示错误原因。

## 状态与数据流

### 本地玩家资料

新增本地资料结构：

```js
{
  playerName: "Chaucer",
  avatarId: "sunflower",
  lastUpdatedAt: 1779420000000
}
```

保存位置：

- `localStorage["pvz-player-profile"]`

用途：

- 登录页填充默认值。
- 房间页展示本端昵称和头像。
- 随 `createRoom` 和 `joinRoom` 消息同步到服务端房间。
- 服务端把轻量资料写入 `roomSnapshot.players.<side>.profile`，供另一台设备展示。

资料同步不是认证系统。服务端只把昵称和头像当作房间展示信息，不把它们用于授权；真实授权仍然依赖 `clientId` 和阵营占位。

### view 状态

前端需要一个独立的页面状态：

```js
{
  view: "login" | "room" | "game",
  profile,
  pendingRoomCode,
  errorMessage
}
```

状态来源：

- URL 查询参数。
- `localStorage` 中的玩家资料。
- `onlinePanelViewModel()` 或在线房间快照。

状态转换：

- 没有玩家资料：进入 `login`。
- 登录完成：进入 `room`。
- 创建或加入成功：停留 `room` 并展示席位。
- 房间进入 `playing`：进入 `game`。
- 游戏页恢复失败：回到 `room` 并提示重新加入。

## 错误处理

登录页：

- 昵称为空时，按钮不可提交或提示 `请输入昵称`。
- 昵称过长时限制输入长度，避免移动端布局破坏。

房间页：

- 房间码为空时提示 `请输入房间码`。
- 房间不存在时提示 `房间不存在或已关闭`。
- 房间满员时提示 `房间已满`。
- WebSocket 连接失败时提示 `联机连接失败，请确认服务仍在运行`。
- 等待房间快照超时时提示 `等待房间响应超时，请重试`。

游戏页：

- 未处于 `playing` 时不展示可操作游戏页，回到房间页或显示等待状态。
- 掉线时显示等待重连，不允许继续提交 gameplay command。

## 视觉资产

本轮新增两张原创配套图片：

- `generated-assets/ui/login-hero.png`：登录页背景图，表现花园入口、植物和僵尸对峙的第一屏氛围。
- `generated-assets/ui/room-panel-hero.png`：房间设置页背景图，表现房间邀请卡、草坪地图和双方阵营席位氛围。

要求：

- 图片必须是原创生成素材，不依赖外部版权素材。
- 图片用于页面氛围，不承担可点击控件职责。
- 控件、文字和房间码必须用 HTML/CSS 渲染，确保清晰可读。
- 移动端图片可以裁剪，但不能遮挡输入框和按钮。

## 测试策略

### 单元测试

新增或更新测试覆盖：

- 玩家资料保存和读取。
- 没有资料时默认进入登录页。
- 有资料且没有房间时进入房间页。
- URL 带房间码时，登录后进入对应房间页。
- 房间状态进入 `playing` 后切换到游戏页。
- 房间未进入 `playing` 时不显示游戏操作入口。

### 在线客户端测试

覆盖：

- 创建房间后房主是植物方。
- 加入者自动成为剩余阵营。
- 房间页不会显示 `undefined` 房间码或 `undefined/2`。
- 双方准备后进入游戏页。
- 游戏页隐藏创建/加入控件。

### 浏览器验收

使用 Playwright 双页面验证：

- 第一台设备登录、创建房间、复制邀请链接。
- 第二台设备打开邀请链接，先登录再进入同一房间。
- 双方在房间页分别显示植物方和僵尸方。
- 双方点击准备后都进入游戏页。
- 植物端种植、僵尸端投放后，双方画面同步。
- 手机宽度下登录页、房间页和游戏页文字不重叠，不出现 `undefined`。

### 回归测试

保留现有：

- `npm test`
- `npm run verify:online-browser -- http://127.0.0.1:5191`

## 验收标准

- 用户打开 `http://192.168.2.15:5191/` 时先看到登录页，而不是直接进入游戏画布。
- 登录页填写昵称后进入房间设置页。
- 房间设置页可以创建房间，显示房间码和邀请链接。
- 第二台设备打开邀请链接后，可以完成登录并进入同一房间。
- 两台设备在房间页分别占据植物方和僵尸方。
- 两台设备都准备后自动进入游戏页。
- 游戏页保留在线同步能力，双方操作仍以服务器权威状态同步。
- 页面在手机和桌面都没有明显文字溢出、控件重叠和 `undefined` 文案。
